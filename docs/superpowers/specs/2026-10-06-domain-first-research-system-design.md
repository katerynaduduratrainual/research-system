# Система дослідження напрямів — дизайн

Дата: 2026-10-06 · Статус: на перегляді редактора · Автор: research-lead

## 1. Навіщо ця перебудова

Рішення редактора від 2026-10-06, на яких стоїть дизайн:

1. **Це система досліджень, а не генерації ідей.** Редактор називає напрям, "куди дує
   вітер". Система вивчає його від основ: попит, бізнес-моделі, гравці, зміни, правила
   входу. Вона вводить редактора і себе в курс і поступово підводить до ідеї. Ідея
   стає виходом процесу, а не входом.
2. **Менше агентів, ширші скіли.** Три агенти: scout, critic, writer. Чотири команди:
   `/explore`, `/research`, `/decide`, `/review`. Решта процедур живе в playbook'ах, які
   лід виконує після звичайних слів редактора.
3. **Система для команди і не прив'язана до Claude.** Протокол лежить у звичайному
   markdown, `.claude/` лише адаптер. Claude Code лишається основним і єдиним
   перевіреним середовищем.
4. **Тестову базу викинути.** Усе, що зібрано до сьогодні, було калібруванням.

Що було не так у v0.5. Корінь системи ідея, тому напрям без ідеї не мав де жити:
B-005 довелося створити з `idea: null`. Сім агентів і одинадцять команд, при цьому
librarian ламався на лімітах, а analyst із доступом до пошуку розмивав провенанс.
Усі правила і ролі лежали під `.claude/`, що не дає працювати з іншого інструменту.

## 2. Цілі й не-цілі

**Цілі**
- Редактор називає напрям і далі лише відповідає на зупинках. Система сама пропонує
  наступні питання за правилами фази.
- Кандидати в ідеї з'являються лише після фаз вступу, карти й фокусу, і лише з
  доказів. До того система ідей не пропонує.
- Кожна процедура описана кроками, які може виконати людина або інший інструмент.
- Гейти не слабшають: без явного "так" редактора нічого не проходить.
- Головна гілка чиста від тестової бази.

**Не-цілі, свідомо відкладено**
- Окремий застосунок чи рантайм на будь-якій моделі.
- Нічні прогони, розклад, сповіщення поза сесією, дашборд.
- Адаптер для Codex чи іншого інструменту з тестовим прогоном.
- Зміна рубрики.
- ID з датою замість послідовних.

## 3. Сутності

### 3.1 Огляд

| Сутність | Шлях | ID | Хто пише |
|---|---|---|---|
| Напрям | `wiki/domains/D-###-<slug>.md` | `D-001` | лід |
| Ідея | `wiki/ideas/I-###-<slug>.md` | `I-001` | лід |
| Brief | `wiki/briefs/B-###-<slug>.md` | `B-001` | лід |
| Доказ | `wiki/evidence/E-<prefix>-<nn>.md` | `E-B001-2-03`, `E-D001-C-01`, `E-ING-20261006-01` | scout, critic, лід (ingest) |
| Джерело | `wiki/sources/S-<hash8>.md` | `S-a1b2c3d4` | scout, critic, лід |
| Тема | `wiki/topics/T-<slug>.md` | `T-local-llm-hardware` | лід |
| Критика | `wiki/critique/<D або I>-critique.md` | за ціллю | critic |
| Аналіз | `wiki/analysis/<I-###>-analysis.md` | за ціллю | writer |
| Звіт | `wiki/reports/R-###-<slug>.md` | `R-001` | writer |

Зникають: план (`wiki/plans/`), звіт скринінгу, папка `wiki/redteam/`. Шаблони
`plan.md`, `screen.md`, `redteam.md` видаляються. Нові шаблони: `domain.md`,
`critique-domain.md`, `critique-idea.md`, `primer.md`, `report-domain.md`. Шаблон
`report.md` стає `report-final.md`.

Посилання між сутностями, як і раніше, подвійними дужками: `[[D-001]]`, `[[E-B001-2-03]]`.

### 3.2 Напрям

```yaml
id: D-000
title: ""
owner: ""             # хто затверджує гейти цього напряму
author: ""            # хто створив
status: active        # active | paused | closed
phase: intro          # intro | map | focus | candidates
checkpoint: null      # null | running | ready
created: 0000-00-00
updated: 0000-00-00
target: null          # yyyy-mm-dd, орієнтир виходу на кандидатів; ставить редактор
confidence:           # low | medium | high | null (ще не досліджували), по шарах
  fundamentals: null
  demand: null
  models: null
  signals: null
  entry: null
briefs: []            # веде scripts/lint.mjs --fix
candidates: []        # I-### ідей, що виросли з напряму; веде lint --fix
reports: []           # веде lint --fix
```

Розділи сторінки:

1. **Чому цей напрям.** Слова редактора, дата.
2. **Межі.** В межах, поза межами, географія, часовий горизонт.
3. **Шари.** П'ять секцій однакової форми: що знаємо з ID доказів і grade, впевненість,
   черга питань із походженням кожного пункту, потрібно від редактора.
   - 1. Основи (`fundamentals`): як влаштована галузь, ланцюжок вартості, хто кому
     платить, масштаб, терміни, технологія.
   - 2. Попит (`demand`): у кого які проблеми, як їх вирішують сьогодні, за що
     платять, скільки їх.
   - 3. Хто й як заробляє (`models`): існуючі бізнес-моделі, ціни, маржа, що з цими
     бізнесами стало.
   - 4. Що змінюється (`signals`): технологія, регуляторика, гроші, що відкрилося
     недавно, що закривається.
   - 5. Вхід і правила (`entry`): закупівлі, сертифікація, ліцензії, бар'єри для
     нового гравця.
4. **Фокус.** Після зупинки карти: 1–3 піднапрями, причина вибору, дата.
5. **Кандидати.** Таблиця: номер, хто, проблема, як, за що платять, докази,
   заперечення критика, стан. Стан: `запропоновано`, `ідея I-###`, `відхилено`.
6. **Фази.** Таблиця з періодом, умовою виходу й станом, див. розділ 4.
7. **Лог.** Дата і подія, один рядок на подію.

### 3.3 Ідея

```yaml
id: I-000
title: ""
domain: null          # D-### або null, якщо редактор приніс ідею напряму
owner: ""
author: ""
stage: active         # active | validation | parked | killed
decision: null        # null | advance | park | kill
checkpoint: null      # null | running | ready
created: 0000-00-00
updated: 0000-00-00
decided: null
target_decision: null # yyyy-mm-dd, ставить редактор
confidence:           # по напрямах роботи
  demand: null
  competition: null
  complexity: null
  economics: null
  entry: null
briefs: []
reports: []
scores:               # 1–5 за docs/rubric.md; null = не оцінено
  fit: null
  market: null
  competition: null
  time_to_revenue: null
  risk: null
  why_us: null
total: null
```

Стадії `inbox`, `screening`, `deep-dive` зникають. Ідея з'являється або з кандидата
напряму через `/decide D-### promote`, або від редактора словами; в обох випадках
вона одразу `active`.

Розділи: гіпотеза одним реченням; звідки ідея, тобто номер кандидата і напрям або
слова редактора; п'ять напрямів роботи тієї самої форми, що шари напряму:
`demand` попит і ринок для цієї ідеї, `competition` конкуренти й альтернативи,
`complexity` складність реалізації, `economics` ціна й юніт-економіка, `entry` шлях
до першого контракту; kill-критерії таблицею зі станом; бали за рубрикою; лог.

Картка ідеї поглинає план: сторінки `wiki/plans/` більше немає. Фаз у ідеї немає, є
дата рішення і черги. Синтез починається, коли редактор каже "синтез".

### 3.4 Brief

```yaml
id: B-000
question: ""
domain: null          # D-### або null
idea: null            # I-### або null
layer: null           # напрям: fundamentals | demand | models | signals | entry
                      # ідея: demand | competition | complexity | economics | entry
                      # null = наскрізний або поза напрямом
author: ""
status: draft         # draft | approved | running | collected
created: 0000-00-00
approved: null
run_stage: null       # queued | scouts | verify | checked | digest | null
run_started: null     # yyyy-mm-ddThh:mm
run_finished: null
reviewed: null        # yyyy-mm-dd, гейт 2 пройдено
budget:
  scouts: 0
  searches_per_scout: 12
  max_sources_per_scout: 10
```

Статус `done` зникає: кінцевий стан це `collected` із заповненим `reviewed`.
`run_stage` втрачає `librarian`, `redteam` і `report`: індекс робить скрипт, а
критика й звіт ідуть через `checkpoint` на напрямі чи ідеї. Brief може мати і
`domain`, і `idea` одночасно, коли ідея виросла з напряму.

Розділи без змін: навіщо, що вже є у wiki, що змінило б рішення, підпитання з IN і
OUT, критерії успіху, журнал прогону, digest.

### 3.5 Доказ, джерело, тема

Доказ: поле `ideas: []` замінюється на два поля, `domain: null` і `idea: null`.
Доказ має принаймні одне з `brief`, `domain`, `idea`; скауту досить заповнити
`brief`, бо напрям і ідея виводяться з нього; доказ без жодного з трьох це помилка
lint. Префікси ID: `E-B###-<sq>-<nn>`
від скаута, `E-D###-C-<nn>` і `E-I###-C-<nn>` від критика в режимі атаки,
`E-ING-<yyyymmdd>-<nn>` від ingest. Решта полів і розділів без змін, включно з
`verified`, `verification` і розділом «Верифікація».

Джерело: без змін, крім розділу «Використано в», який видаляється: список
виводиться з доказів за потреби через grep, тримати його руками чи скриптом не варто.

Тема: `ideas: []` замінюється на `domains: []`. Решта без змін. Теми лишаються
накопиченим знанням, яке переживає напрями: новий напрям починається з читання тем.

### 3.6 Критика

```yaml
target: D-000         # D-### або I-###
author: critic
created: 0000-00-00
updated: 0000-00-00
spotcheck: {ok: 0, inexact: 0, failed: 0}
```

Шаблон `critique-domain.md`: де твердження про гроші найслабші; аудит доказів по
шарах, тобто які шари тримаються на джерелах C і D і які числа є заявами вендорів;
вибіркова перевірка п'яти сторінок, включно з тими, що режим verify позначив `ok`;
кого немає в доказах, тобто інкумбенти, регулятор, "нічого не робити", субститути,
суміжні гравці; сигнали, які мають докази грошей, і сигнали, які мають лише пресу;
заперечення до кожного кандидата й один факт, що його вбив би, якщо кандидати є;
що карта не покриває; один факт, який змінив би картину найбільше.

Шаблон `critique-idea.md`: нинішній `redteam.md` без поля `mode`: pre-mortem, аудит
доказів, перевірка джерел, кого немає, kill-критерії, атака на припущення аналізу,
один факт.

### 3.7 Аналіз

Нинішній `analysis.md` з `author: writer`. Розділ «Основа для плану MVP» лишається
завжди, бо плану як окремої сутності немає, а гіпотеза MVP береться з картки ідеї.

### 3.8 Звіт

```yaml
id: R-000
target: D-000         # D-### або I-###
type: primer          # primer | domain | final
author: writer
created: 0000-00-00
confidence: medium    # high | medium | low
confidence_set_by: "" # grade доказів | чутливість аналізу | spot-check критика
total_score: null     # лише final
briefs: []
```

Три шаблони:
- `primer.md`, конспект напряму на 2–4 сторінки: як влаштовано, тобто ланцюжок
  вартості і хто кому платить; масштаб і структура з числами; гравці й сегменти;
  терміни; що змінилося за п'ять років; чого ми ще не знаємо; що читати далі, тобто
  найкращі джерела з grade. Кожне речення з тегом доказу.
- `report-domain.md`, стан напряму на зупинці: що знаємо по шарах із впевненістю; де
  гроші; що слабке за критикою; кого немає; кандидати з запереченнями, якщо фаза
  фокусу або пізніше; відкриті питання; наступний крок дослідження.
- `report-final.md`, нинішній `report.md`: відповідь у три речення, впевненість, бали,
  ключові докази, контраргументи критика, що змінило б висновок, план MVP.

## 4. Трек напряму

Чотири фази. Кожна закінчується зупинкою, на якій редактор бачить результат у чаті
й каже, що далі. Орієнтири тривалості: вступ 1–2 тижні, карта 2–4, фокус 2–6.
Дату `target` ставить редактор, kill можливий на будь-якій зупинці.

### 4.1 Вступ (`intro`)

1. Редактор називає напрям. Лід ставить до трьох питань: чому цей напрям, що в
   межах і поза межами, орієнтовна дата виходу на кандидатів.
2. Лід створює сторінку напряму і читає теми wiki, які торкаються напряму. Те, що
   вже відомо, записує в шар основ.
3. Лід пише вступний brief із `layer: fundamentals` і 4–6 підпитаннями: як влаштована
   галузь і ланцюжок вартості; масштаб і структура; сегменти й гравці; терміни й
   технологія; що змінилося за п'ять років; де про це читати.
4. Гейт 1, прогін із двома зупинками, гейт 2. Знання лягає в шар основ і в теми.
5. Writer пише конспект. Критика перед конспектом не потрібна: сторінки вже
   перевірені під час прогону.
6. **Зупинка фази.** Редактор прочитав конспект і каже: "карта", "змінити межі" або
   "закрити". Умова виходу: сказано "карта".

### 4.2 Карта (`map`)

1. Лід пропонує по одному широкому brief'у на кожен із шарів 2–5. Редактор вибирає,
   додає своє, переставляє. Одночасно біжать не більше двох.
2. Кожен brief проходить гейт 1, прогін, гейт 2. Після гейту 2 лід оновлює шар:
   що знаємо, впевненість, черга.
3. Умова виходу: кожен із шарів 2–5 має переглянутий brief або записане в лог
   "пропустити" від редактора.
4. Зупинка фази йде ланцюжком: critic атакує карту, writer пише звіт стану напряму.
5. **Зупинка фази.** Редактор бачить у чаті: що знаємо по шарах, де гроші, три
   найсильніші заперечення критика, результат вибіркової перевірки. Варіанти:
   "фокус на …" з назвою 1–3 піднапрямів, "ще раунд по шару …", "змінити межі",
   "закрити". Вибір фокусу записується через `/decide D-### focus`.

### 4.3 Фокус (`focus`)

1. Лід пише в розділ «Фокус» вибрані піднапрями з причиною і створює для них пункти
   в чергах відповідних шарів.
2. Лід пропонує глибші brief'и: конкретні сегменти й проблеми, хто пробував і що
   вийшло, собівартість, реальні ціни. У секції «Потрібно від редактора» лід готує
   питання для розмов у полі; розмови веде редактор, записи заходять через ingest.
3. Умова виходу: редактор каже "досить" або черги фокусу порожні.
4. Зупинка фази йде ланцюжком. Спершу лід пише або оновлює розділ «Кандидати»: з
   доказів карти, кожен кандидат має принаймні один доказ про проблему і один про
   те, хто за це платить. Якщо жодного кандидата обґрунтувати не можна, лід так і
   пише, і зупинка все одно проводиться. Потім critic атакує карту і кандидатів.
   Потім writer пише звіт із кандидатами й запереченнями.
5. **Зупинка фази.** Редактор бачить кандидатів із запереченнями. Варіанти:
   "promote <n>", "drop <n>", "ще копати", "закрити". Перший promote переводить
   напрям у фазу кандидатів.

### 4.4 Кандидати (`candidates`)

Напрям лишається відкритим: можна запускати нові brief'и, на наступній зупинці
з'являються нові кандидати, промоції й відхилення йдуть через `/decide`. Умова
виходу: редактор закриває напрям через `/decide D-### close`.

## 5. Трек ідеї

1. `/decide D-### promote <n>` створює ідею: гіпотеза з рядка кандидата, `domain`,
   `owner` власника напряму, kill-критерії з заперечень критика до цього кандидата.
   Редактор може принести ідею і словами; тоді `domain: null`.
2. `/explore I-###` показує напрями роботи й пропонує brief'и на те, що специфічне
   для ідеї; докази напряму перевикористовуються через розділ brief'у «Що вже є у
   wiki». Перша пропозиція для свіжої ідеї це пресет "швидка перевірка": три
   підпитання, попит, конкуренти, здійсненність і відповідність, по 8 пошуків.
3. Редактор каже "синтез", або лід пропонує синтез, коли черги порожні чи близько
   `target_decision`. Ланцюжок: writer пише аналіз, critic атакує, writer пише
   фінальний звіт.
4. **Гейт 3.** Редактор бачить відповідь у три речення, впевненість, бал, головний
   ризик, план MVP. Варіанти: advance, park, kill, "ще досліджувати". Рішення
   записує `/decide I-###`.

## 6. Гейти і зупинки

Три гейти лишаються: brief затверджено, докази переглянуто, рішення записано.

| Де | Що бачить редактор | Варіанти |
|---|---|---|
| brief, гейт 1 | brief у 12 рядках | затвердити · змінити підпитання · звузити · стоп |
| прогін, зупинка після збору | докази по підпитаннях, перевірка, 2–3 знахідки | продовжити · перезапустити скаута · додати підпитання · стоп |
| прогін, зупинка після digest'у, гейт 2 | digest у 12 рядках | далі · копати глибше · додати підпитання · стоп |
| напрям, після вступу | конспект | карта · змінити межі · закрити |
| напрям, після карти | стан напряму й критика | фокус на … · ще раунд · змінити межі · закрити |
| напрям, після фокусу | кандидати з запереченнями | promote n · drop n · ще копати · закрити |
| ідея, гейт 3 | фінальний звіт | advance · park · kill · ще досліджувати |

Формат зупинки без змін: до 12 рядків простими словами, що маємо і що далі, потім
питання з конкретними варіантами, жоден не позначений як рекомендований, думка ліда
йде в тексті перед питанням. Завершений крок ніколи не зводиться до команди для
введення. Коли зупинка настала, поки редактора не було, `/review` відкриває її.

## 7. Агенти

Три ролі. Файли ролей лежать в `agents/`, кожен із frontmatter, який розуміє Claude
Code: `name`, `description`, `tools`, `model`.

### 7.1 scout

Без змін по суті: одне підпитання, пошук, сторінки доказів і джерел, повернення
лише ID і однорядкових тверджень. Зміни:
- перед пошуком читає сторінку напряму або ідеї і теми, які там названі;
- для brief'у з `layer: fundamentals` позначає в поверненні рядок «Для конспекту:
  S-…», тобто найкращі джерела для читання;
- у сторінці доказу заповнює `domain:` замість `ideas:`.
Інструменти: WebSearch, WebFetch, Read, Write, Glob, Grep, Bash. Модель opus.

### 7.2 critic

Один файл, два режими. Режим і ціль задаються в завданні.

**`verify B-### <sq> <сьогодні>`.** Нинішня процедура verifier без змін: список
сторінок, перевитяг числа, три перевірки, вердикт на сторінці доказу, повернення з
підсумком. Нічого окремого не пише.

**`attack D-### | I-###`.** Читає сторінку цілі, digest'и її brief'ів, усі докази,
аналіз для ідеї, кандидатів для напряму. Ніколи не читає `wiki/reports/`. Пише
`wiki/critique/<ціль>-critique.md` за шаблоном напряму або ідеї. Нові докази, які
збирає, пишуться як `E-<ціль>-C-<nn>`. Для напряму окремо: вибіркова перевірка
включає сторінки, які режим verify позначив `ok`, бо critic у режимі атаки перевіряє
й самого себе в іншому контексті. Повернення до 10 рядків: три головні заперечення,
скільки сторінок знизив би, підсумок перевірки, один факт.

Інструменти: Read, Glob, Grep, WebFetch, WebSearch, Edit, Write, Bash. Модель inherit,
тобто найсильніша доступна.

### 7.3 writer

Без інтернету. Чотири виходи, вихід і ціль задаються в завданні разом з ID звіту.

- **`primer D-###`.** Передумова: вступний brief напряму має `reviewed`. Пише
  `wiki/reports/R-###-<slug>.md` типу `primer`.
- **`analysis I-###`.** Нинішня процедура analyst без пошуку: кожне число це ID
  доказу або рядок у таблиці припущень; де немає ні того, ні іншого, пише
  "невідомо" і додає питання у `wiki/open-questions.md`.
- **`report D-###`.** Передумова: критика напряму новіша за дату `reviewed`
  найновішого brief'у напряму. Тип `domain`.
- **`report I-###`.** Передумова: критика ідеї новіша за аналіз. Тип `final`.

Якщо передумова не виконана, повертає один рядок, що саме відсутнє, і зупиняється.
Кожне фактичне речення закінчується ID доказів; речення без тегу або видаляється,
або стає "доказів не знайдено". Інструменти: Read, Glob, Grep, Write, Bash. Модель
opus.

### 7.4 Лід

Головна розмова, без файлу агента. Пише brief'и, digest'и, складає знання в шари й
теми, пише кандидатів, ставить бали за рубрикою, питає на зупинках, запускає
скрипти. Не збирає докази сам, не вирішує, не задає порядок денний. Його правила це
`AGENTS.md`.

## 8. Команди і playbook'и

Принцип: протокол живе в `playbooks/`, команди це псевдоніми. Лід відповідає на
звичайні слова редактора і виконує відповідний playbook. Команда потрібна для
двох речей: щоб людина з команди мала зрозумілий вхід і щоб скіл спрацював точно.
`/decide` обов'язково команда, бо це єдиний спосіб записати в decision log.

| Playbook | Команда | Коли спрацьовує словами |
|---|---|---|
| `explore.md` | `/explore` | "вивчаємо напрям …", "де ми по D-001", "що далі по ідеї" |
| `research.md` | `/research` | "дослідь питання …", "продовж B-007" |
| `decide.md` | `/decide` | лише командою |
| `review.md` | `/review` | "що чекає на мене", "показуй B-004" |
| `checkpoint.md` | немає | "так" на пропозицію зупинки фази; "синтез"; "зроби звіт"; "атакуй карту" |
| `ingest.md` | немає | посилання або файл зі словами "ось джерело", "поклади в raw" |

Назва `/review` замість `/status`, бо `/status` зарезервовано в Claude Code.
Запасна назва, якщо колись знадобиться: `/desk`.

Спільні правила для всіх playbook'ів: кожен субагент стартує у фоні; перед стартом
стан записується у файл, тобто `run_stage` на brief'і або `checkpoint` на напрямі чи
ідеї; після старту лід каже одним реченням, що запущено, що воно дасть і приблизно
скільки триватиме, і закінчує хід; на сповіщення про завершення лід перечитує стан
із файлу і робить наступний крок ланцюжка; на зупинці лід звітує і чекає. Коміт
після кожного кроку, push на гейтах через запит дозволу.

### 8.1 `/explore`

**Новий напрям, `/explore "<назва>"`.**
1. Лід ставить до трьох питань: чому цей напрям, що в межах і поза межами,
   орієнтовна дата виходу на кандидатів.
2. Лід бере ID через `next-id D`, створює сторінку з `templates/domain.md`:
   мотив словами редактора, межі, порожні шари, фази, лог. `phase: intro`,
   `owner` і `author` це редактор.
3. Лід читає теми wiki, які торкаються напряму, і записує відоме в шар основ.
4. Лід пише вступний brief за кроками 1–2 playbook'у research з `domain: D-###`,
   `layer: fundamentals` і 4–6 підпитаннями з розділу 4.1.
5. Гейт 1 за кроком 3 playbook'у research. Після "затвердити" лід робить коміт
   `domain(D-###): created` і стартує прогін за кроками 4–9.

**Існуючий напрям, `/explore D-###`.**
1. Лід запускає `node scripts/status.mjs` і показує до 15 рядків: фаза і тиждень,
   по шарах впевненість і довжина черги, що біжить, що чекає на редактора.
2. Якщо щось цього напряму чекає на редактора, лід каже про це першим і відкриває
   зупинку за playbook'ом review.
3. Якщо умова виходу з фази виконана, лід пропонує зупинку фази. На "так" виконує
   playbook checkpoint.
4. Інакше лід пропонує 1–3 наступні brief'и за правилом фази: у вступі нічого до
   конспекту; у карті по одному широкому brief'у на кожен шар без переглянутого
   brief'у; у фокусі з черг фокусу; у кандидатах лише по ідеях. Редактор вибирає,
   додає своє, переставляє.
5. Для кожного вибраного лід пише brief за кроками 1–2 playbook'у research і
   проводить гейт 1 для всіх в одному раунді. Затверджені стартують, не більше двох
   одночасно, решта `run_stage: queued`.
6. Лід закінчує хід повідомленням простими словами: що запущено, що дасть, скільки
   приблизно триватиме.

**Ідея, `/explore I-###`.** Ті самі кроки з напрямами роботи замість шарів. Для
свіжої ідеї перша пропозиція це пресет "швидка перевірка" з розділу 5. Коли черги
порожні або близько `target_decision`, лід пропонує синтез; на "так" виконує
playbook checkpoint для ідеї.

**Правки словами.** "додай питання …", "підніми … нагору", "пропусти шар …",
"зміни дату", "пауза", "продовжуємо". Лід редагує сторінку, дописує лог, ставить
`updated`, робить коміт `domain(D-###): <що>`. Гейту немає: це сторінка редактора.

### 8.2 `/research`

**Нове питання, `/research "<питання>" [D-### | I-###]`.**
1. Лід читає сторінку напряму або ідеї, теми, які там названі, і шукає ключові слова
   у brief'ах і доказах. Знайдене записує в розділ «Що вже є у wiki». Якщо питання
   вже закрите, каже про це й пропонує перевикористати або розширити.
2. Лід пише brief із `templates/brief.md`: питання одним реченням, навіщо, що
   змінило б рішення, 3–7 незалежних підпитань із IN, OUT і джерелами спробувати
   першими, бюджет, критерії успіху. `status: draft`. Якщо питання неоднозначне щодо
   меж, географії чи горизонту, до трьох уточнень перед написанням.
3. **Зупинка, гейт 1.** Лід показує brief у 12 рядках і питає: затвердити, змінити
   підпитання, звузити, стоп. На "затвердити": `status: approved`, коміт
   `brief(B-###): <slug>`.
4. Якщо вже біжать два brief'и, цей отримує `run_stage: queued`, лід каже, на що він
   чекає, і зупиняється. Інакше `status: running`, `run_stage: scouts`,
   `run_started`, рядок у журналі. Стартують скаути, по одному на підпитання, усі в
   цьому ході, усі у фоні. Лід каже, що запущено, і закінчує хід.
5. Скаут завершив: лід одразу стартує critic у режимі verify для цього підпитання,
   не чекаючи на інших. На першому verify `run_stage: verify`. Скаут, що зупинився
   без звіту, один раз отримує повідомлення написати сторінки з уже прочитаного.
6. **Зупинка після збору.** Усі скаути й усі verify завершені: `run_stage: checked`.
   Лід пише до 12 рядків: докази по підпитаннях із grade, підсумок перевірки і кожна
   знижена сторінка з причиною, 2–3 головні знахідки словами, скаути, що не дійшли.
   Питання: продовжити, перезапустити скаута №, додати підпитання, стоп.
7. На "продовжити": `run_stage: digest`. Лід запускає `node scripts/lint.mjs --fix`
   і `node scripts/index.mjs`; помилки lint виправляє сам. Пише digest у brief: по
   підпитанню 3–5 знахідок із ID і grade, підсумок перевірки, протиріччя,
   прогалини, зачіпки для інших скаутів, витрачений бюджет. Складає нове знання в
   теми: оновлює або створює сторінки тем. `status: collected`, `run_stage: null`,
   `run_finished`. Коміт `run(B-###): <n> evidence, <m> sources, <k> topics`.
8. **Зупинка після digest'у, гейт 2.** Одразу, в цьому ході: digest у 12 рядках і
   питання: далі, копати глибше в підпитання №, додати підпитання, стоп.
9. На "далі": `reviewed: <сьогодні>`. Лід оновлює шар напряму або напрям роботи
   ідеї: що знаємо з ID, впевненість із причиною в одне речення, відмічені пункти
   черги, нові пункти з прогалин і зачіпок, пункти для редактора. Коміт
   `review(B-###): gate 2`, push. Якщо чекає brief у черзі, він стартує.

Хвости двох brief'ів, тобто крок 7, ідуть по одному, бо пишуть спільні файли.

**Продовження, `/research B-###`.** `run_stage: checked` або `collected` без
`reviewed` означає відкрити відповідну зупинку. `status: running` означає відновити:
скаути лише для підпитань без доказів, verify лише для неперевірених, далі
ланцюжок із відповідного кроку, рядок "відновлено" в журналі.

**Доповнення.** "копати глибше" і "додати підпитання" на гейті 2 дописують нові
підпитання в brief під заголовком із датою, після короткого підтвердження стартує
той самий ланцюжок лише для них; `reviewed` повертається в `null`.

### 8.3 `checkpoint`

Виконується після "так" редактора на пропозицію зупинки фази, після слів "синтез",
"зроби звіт", "атакуй карту", або коли редактор просить це будь-якими словами.
Передумова: ціль має хоча б один brief із `reviewed`; інакше лід каже, чого бракує.

**Напрям у фазі вступу.**
1. `checkpoint: running`, рядок у лозі. Writer `primer D-###` у фоні з ID звіту з
   `next-id R`. Лід каже, що стартувало.
2. Writer завершив: lint, index, коміт `report(R-###): primer D-###`,
   `checkpoint: ready`, лог.
3. Лід показує конспект у 12 рядках і питає: карта, змінити межі, закрити.
4. На "карта": `phase: map`, `checkpoint: null`, лог, коміт, push.

**Напрям у фазі карти.**
1. `checkpoint: running`, лог. Critic `attack D-###` у фоні.
2. Critic завершив: writer `report D-###` у фоні.
3. Writer завершив: lint, index, коміт `report(R-###): domain D-###`,
   `checkpoint: ready`, лог.
4. Лід показує до 12 рядків: що знаємо по шарах, де гроші, три найсильніші
   заперечення, підсумок вибіркової перевірки. Питання: фокус на …, ще раунд по
   шару …, змінити межі, закрити.
5. На "фокус": кроки `/decide D-### focus`, `phase: focus`, `checkpoint: null`.

**Напрям у фазі фокусу або кандидатів.**
1. Лід пише або оновлює розділ «Кандидати» за правилом розділу 4.3. Коміт
   `domain(D-###): candidates`.
2. `checkpoint: running`, лог. Critic `attack D-###` у фоні; critic бачить кандидатів.
3. Critic завершив: writer `report D-###` у фоні.
4. Writer завершив: lint, index, коміт, `checkpoint: ready`, лог. Лід переносить
   заперечення критика в таблицю кандидатів.
5. Лід показує кандидатів із запереченнями. Питання: promote n, drop n, ще копати,
   закрити. Кожен вибір іде через `/decide`. `checkpoint: null`.

**Ідея.**
1. `checkpoint: running`, лог. Writer `analysis I-###` у фоні.
2. Writer завершив: critic `attack I-###` у фоні.
3. Critic завершив: writer `report I-###` у фоні з ID з `next-id R`.
4. Writer завершив: lint, index, коміт `report(R-###): final I-###`,
   `checkpoint: ready`, лог.
5. **Гейт 3.** Лід показує відповідь у три речення, впевненість і що її задало,
   бал, головний ризик, план MVP. Питання: advance, park, kill, ще досліджувати.
   Рішення через `/decide I-###`; "ще досліджувати" нічого не записує.

**Лише критика.** На "атакуй карту" або "атакуй ідею": лише кроки 1–2 відповідного
ланцюжка, потім повернення критика в чаті, `checkpoint: null`. Звіт не пишеться.

### 8.4 `ingest`

Спрацьовує, коли редактор дає посилання або файл і каже, що це джерело, або
вставляє свої нотатки з розмови.
1. Лід читає URL або файл. Зберігає копію в `raw/<yyyy-mm-dd>-<slug>.md` із
   заголовком за `raw/README.md`, `added_by: user`. Існуючий файл не перезаписує.
2. `node scripts/source-id.mjs` і сторінка джерела за шаблоном, з grade.
3. 3–10 сторінок доказів з ID `E-ING-<yyyymmdd>-<nn>`, з `domain` або `brief`, якщо
   редактор назвав; протиріччя з наявними доказами через `contradicts`.
4. Critic у режимі verify для нових ID у фоні. Лід каже одним рядком: джерело з
   grade, скільки доказів, перевірка пішла. Хід закінчується.
5. Verify завершив: лід складає нове в теми й у сторінку напряму або ідеї, тобто
   «Що знаємо», відмічені пункти черги, закриті пункти «Потрібно від редактора».
   Lint, index, коміт `ingest(S-<hash8>): <slug>`. Лід пише до 6 рядків: ID доказів
   з твердженнями, підсумок перевірки, знайдені протиріччя.

### 8.5 `/decide`

Єдиний спосіб змінити `docs/decision-log.md`. Без причини одним реченням рішення
не записується.

Ідея, `/decide I-### advance|park|kill "<причина>"`: як зараз. Запис у лог, картка:
`decision`, `decided`, `stage`, тобто advance → `validation`, park → `parked`,
kill → `killed`. Коміт `decide(I-###): <рішення>`, push.

Напрям:
- `focus "<піднапрями>" "<причина>"`: розділ «Фокус», пункти черг, `phase: focus`.
- `promote <n> "<причина>"`: створює ідею за розділом 5, стан кандидата
  `ідея I-###`, `candidates` напряму, перший promote дає `phase: candidates`.
- `drop <n> "<причина>"`: стан кандидата `відхилено`.
- `pause`, `continue`, `close "<причина>"`: `status` напряму.

Запис у decision log для напряму:
```
## <yyyy-mm-dd> · D-### · <focus|promote|drop|pause|continue|close>
- Хто: <owner>
- Рішення: <дія> — <причина словами редактора>
- На основі: [[R-###]] (звіт) або «звіту немає — рішення редактора»; критика: <головне заперечення>
- Що б змінило рішення: <із звіту або критики>
```

Після запису: коміт, push, `node scripts/index.mjs`.

### 8.6 `/review`

- Без аргументу: `node scripts/status.mjs`. До 20 рядків: що чекає на редактора,
  кожен пункт словами, що саме там є; що біжить із кроком і часом; напрями з фазою
  і впевненістю по шарах; ідеї за стадіями; brief'и з наступним кроком; рядок lint.
- З ID brief'у: відкриває зупинку після збору або гейт 2 за playbook'ом research.
- З ID напряму: `checkpoint: ready` означає показати зупинку фази за playbook'ом
  checkpoint. Інакше стан напряму.
- З ID ідеї: `checkpoint: ready` означає гейт 3. Інакше стан ідеї.
- Push у кінці, якщо гейт пройдено.

## 9. Скрипти

Усе на Node 20+ без залежностей, як зараз. Тести на `node:test` у `scripts/tests/`.

- **`lint.mjs`.** Нові перевірки. Напрям: шлях і `id` узгоджені, `status`, `phase`,
  `checkpoint` з переліків, п'ять ключів `confidence`, `owner` на активному напрямі.
  Ідея: `stage` з нового переліку, `domain` існує, п'ять ключів `confidence`. Brief:
  `layer` допустимий для свого напряму чи ідеї, `run_stage` з нового переліку,
  `author`; коли задано і `domain`, і `idea`, `layer` перевіряється за переліком
  ідеї. Доказ: є принаймні одне з `brief`, `domain`, `idea`; ID за одним із трьох
  шаблонів. Звіт:
  `type` з переліку; для `domain` критика цілі новіша за найновіший `reviewed`
  brief цілі, для `final` новіша за аналіз, інакше помилка. Критика: ціль існує.
  Тема: `domains`. Перевірки планів видаляються. Попередження лишаються.
  Прапорець `--fix` виправляє лише виведені поля: `briefs`, `reports`, `candidates`
  на напрямах і ідеях, `status: stale` на темах, зворотні посилання `contradicts`.
- **`index.mjs`, новий.** Переписує `wiki/index.md`: напрями з фазою, власником,
  впевненістю, кількістю brief'ів і датою; ідеї за стадіями з балом; теми; відкриті
  brief'и; останні звіти; лічильники доказів і джерел за grade.
- **`status.mjs`.** Блоки: чекає на вас, тобто гейт 1, зупинка після збору, гейт 2,
  зупинки фаз напрямів, гейт 3 ідей; біжить, тобто brief'и в ланцюжку з кроком і
  часом, checkpoint'и; напрями з фазою, тижнем, впевненістю, чергами; ідеї; brief'и;
  лічильники. Прапорець `--waiting` як зараз. Блок планів зникає.
- **`next-id.mjs`.** Додається префікс `D`.
- **`source-id.mjs`, `now.mjs`.** Без змін.
- **`hooks/critique-gate.mjs`.** Перейменований `redteam-gate.mjs`: блокує запис у
  `wiki/reports/` для `type: domain` і `type: final` без свіжої критики за тим самим
  правилом, що lint. Конспект пропускає. Лишається лише в адаптері Claude.

## 10. Файли: протокол і адаптер

```
AGENTS.md        правила системи, колишній CLAUDE.md
CLAUDE.md        один рядок: @AGENTS.md
agents/          scout.md, critic.md, writer.md
playbooks/       explore.md, research.md, checkpoint.md, ingest.md, decide.md, review.md
templates/       domain, idea, brief, evidence, source, topic, critique-domain,
                 critique-idea, analysis, primer, report-domain, report-final
scripts/         lint, index, status, next-id, source-id, now, hooks/, tests/
docs/            vision.md, workflow.md, context.md, rubric.md, decision-log.md, superpowers/
wiki/            domains, ideas, briefs, evidence, sources, topics, critique, analysis, reports
raw/
.claude/         agents/<role>.md → ../../agents/<role>.md (symlink)
                 skills/<cmd>/SKILL.md → ../../../playbooks/<cmd>.md (symlink)
                 settings.json, hooks через settings
```

Правила:
1. Файли в `agents/` і `playbooks/` це єдине джерело правди. Їхній frontmatter
   розуміє Claude Code, тобто `name`, `description`, `tools`, `model` для агентів і
   `name`, `description`, `argument-hint`, `disable-model-invocation` для команд.
   Інші інструменти frontmatter ігнорують.
2. `.claude/agents/` і `.claude/skills/` це symlink'и. Перший крок впровадження
   перевіряє, що Claude Code їх читає. Якщо ні, замість symlink'ів буде
   `scripts/sync-adapters.mjs`, який копіює файли в `.claude/` однією командою, і
   коміт-хук, що нагадує його запустити.
3. `AGENTS.md` містить: мову, правила, що не обговорюються, схему, делегування,
   формат зупинок, чого лід не робить, і розділ "Без Claude Code": як людина або
   інший інструмент виконує роль, відкриваючи `agents/<роль>.md` як інструкцію для
   нової сесії із завданням у тому форматі, що описаний у playbook'у. Фонові
   агенти й сповіщення є лише в Claude Code; в іншому середовищі ті самі кроки
   йдуть один за одним.
4. Гейт "критика перед звітом" працює без Claude через правило lint; hook це друга
   лінія лише для Claude.
5. `settings.json` лишається адаптером: дозволи на `wiki/**`, `raw/**`, `docs/**`,
   скрипти і git без push; заборона `rm -rf`; hook.

## 11. Команда

1. На напрямі й ідеї поле `owner`. Гейти напряму затверджує його власник. Інші
   члени команди можуть пропонувати brief'и, тобто писати їх у `draft`, і запускати
   затверджені.
2. На brief'ах, звітах, критиці і в decision log поле або рядок `author` чи «Хто»:
   хто був редактором цього кроку.
3. `wiki/index.md` генерує `scripts/index.mjs`. Руками його не редагують; після
   злиття гілок перегенерувати.
4. `wiki/open-questions.md` і `docs/decision-log.md` лише дописуються в кінець.
5. ID послідовні. Lint ловить дублі як помилку. Правило: нову сутність створюють на
   свіжому `main`. Якщо паралельно працюватимуть більше трьох людей, перехід на ID
   з датою буде окремим рішенням.
6. Протокол називає ролі, не моделі. Адаптер Claude ставить `opus` скауту й writer,
   `inherit` критику. Інший інструмент бере свою найсильнішу модель; нічого слабшого
   за найсильніше доступне, за рішенням редактора від 2026-10-05.
7. Робота на `main`, короткі гілки за потреби. Push на гейтах через запит дозволу,
   без змін.
