# Фонові прогони і план дослідження на 1–3 місяці — дизайн

Дата: 2026-10-05 · Статус: на перегляді редактора · Автор: research-lead

## 1. Проблема

1. **Редактор чекає.** `/run` синхронний: крок 3 каже «Wait for all scouts. Do not
   summarise partial results to the user», далі так само послідовно verifier →
   librarian → lint → digest → теми. Прогін B-003 15.09.2026 зайняв ≈ 2 год 20 хв від
   коміту brief'у (12:56) до останнього коміту (15:18). Увесь цей час сесія зайнята.
2. **Горизонт — один день.** Найбільша одиниця планування — brief (години). I-001
   пройшла від ідеї до park за один день (09.09.2026). Стадія validation у
   `docs/vision.md` описана одним рядком, без сутності, шаблону чи команди. Плану на
   ідею, довшого за один прогін, немає.

## 2. Рішення редактора, на яких стоїть дизайн (2026-10-05)

- Результат роботи над одним продуктом за 1–3 місяці: **рішення (advance / park /
  kill) + план MVP** (перший клієнт, обсяг MVP, ціна, шлях входу).
- **Ідеї веде редактор.** Система — дослідницький бек-офіс навколо ідеї: ринок,
  конкуренти, складність, маржинальність, регуляторика. Вона не керує портфелем і не
  видає редакторові завдань.
- Ритм: **у межах сесії.** Задача йде у фоні, сесія вільна, повідомлення коли готово.
- Обраний підхід: **фон + план дослідження по ідеї**, мінімум нової інфраструктури.
- `git push` виконується **на гейті**, а не після кожного коміту (зміна правила 8,
  рішення від 2026-09-09).

## 3. Цілі й не-цілі

**Цілі**
- Жоден крок із субагентами не блокує сесію.
- Питання гейту чекає на редактора, а не редактор на питання.
- Стан прогону живе у файлах; обрив сесії нічого не губить.
- Ідея на довгому треку має план: напрями, що відомо, черга питань, фази, дата
  цільового рішення.
- Гейти не слабшають: без явного «так» редактора за гейт нічого не проходить.

**Не-цілі (свідомо відкладено)**
- Нічні прогони, розклад, окремий процес-виконавець.
- Сповіщення поза сесією, дашборд.
- Зміна рубрики (критерію про економіку в ній немає; див. розділ 12).
- Перейменування стадій ідеї.

## 4. Частина A — фонове виконання

### 4.1 Правило
Кожен субагент запускається у фоні. Skill, що запускає агентів, робить три речі:
записує стан у файл, одним рядком повідомляє редактора, повертає керування. Наступний
крок ланцюжка виконується, коли приходить сповіщення про завершення агента.

### 4.2 Ланцюжок `/run B-###`
1. Перевірка `status: approved`. Якщо вже біжать два brief'и — `run_stage: queued`,
   повідомлення «стартує після завершення B-###», кінець.
2. `status: running`, `run_stage: scouts`, `run_started: <дата й час>`. Скаути всіх
   підпитань стартують у фоні в одному ході. Редакторові: один рядок «запущено» і до
   трьох пропозицій із `node scripts/status.mjs --waiting`.
3. Скаут підпитання N завершився → одразу стартує verifier підпитання N, не чекаючи
   решти скаутів. Коли стартував перший verifier — `run_stage: verify`.
4. Усі verifier'и завершились → `run_stage: librarian` → librarian (повний режим) →
   lint; якщо є помилки, librarian ще раз із виводом lint.
5. `run_stage: digest` → lead пише `## Digest`, складає нове знання в `wiki/topics/`,
   коміт `run(B-###): …`.
6. `status: collected`, `run_stage: null`, `run_finished: <дата й час>`. Редакторові
   один рядок: «B-### готовий до перегляду: `/review B-###`». Без `AskUserQuestion`.
7. Якщо є brief із `run_stage: queued`, стартує найстаріший.

Кожен перехід дописує рядок у розділ `## Журнал прогону` brief'у (час, крок, коротко
що сталося). Звідси береться тривалість кожного кроку.

### 4.3 Нові поля brief'у
```yaml
workstream: null      # demand | competition | complexity | economics | entry | null
run_stage: null       # queued | scouts | verify | librarian | digest | redteam | report | null
run_started: null     # yyyy-mm-ddThh:mm
run_finished: null    # yyyy-mm-ddThh:mm
reviewed: null        # yyyy-mm-dd — гейт 2 пройдено
```
`redteam` і `report` використовує лише `/screen`. Значення `status` не змінюються.

### 4.4 Інші skills
- `/screen`: кроки 1–2 як зараз, далі той самий фоновий ланцюжок; після digest —
  бали lead'а → red team lite (`run_stage: redteam`) → writer (`run_stage: report`) →
  коміт → brief `status: done`, `run_stage: null`. Редакторові: «R-### готовий:
  `/review I-###`». Гейт 3 — на вимогу.
- `/red-team`, `/report`, `/ingest`, `/decide`, `/lint`: агент у фоні, один рядок на
  старті й один на завершенні.

### 4.5 Паралельність
- Одночасно біжать не більше двох brief'ів; третій стає в чергу (`queued`).
- Скаути й verifier'и різних brief'ів можуть перетинатись: ID доказів мають префікс
  brief'у, ID джерел — хеш URL.
- Хвіст (librarian → lint → digest → теми → коміт) пише у спільні файли, тому хвости
  виконуються по одному: другий чекає на `run_stage: librarian`.

### 4.6 Що lead показує під час прогону
Проміжних знахідок не показує: неверифіковане число ще не доказ. На запит показує
прогрес із файлів: крок, скільки підпитань уже мають докази, скільки верифіковано.

### 4.7 Відновлення
`/run B-###` на brief'і зі `status: running` продовжує з `run_stage`: для кожного
підпитання перевіряє, чи є сторінки доказів і чи заповнене `verification:`, і
перезапускає лише відсутнє. Інструкція «на сповіщення про завершення агента прочитай
`run_stage` і зроби наступний крок» живе в `CLAUDE.md`, щоб пережити стискання
контексту.

## 5. Частина B — гейти на вимогу

Новий skill `/review` — єдине місце, де редактор проходить відкладені гейти.

| Виклик | Що робить |
|---|---|
| `/review` | Список усього, що чекає, з точною командою для кожного пункту |
| `/review B-###` | Гейт 2: заголовок digest'у ≤ 12 рядків, `AskUserQuestion`: далі / копати глибше в №… / додати підпитання / стоп |
| `/review I-###` | Гейт 3 для звіту скринінгу або фінального звіту; або контрольна точка фази плану |

- **Гейт 2 пройдено** → `reviewed: <дата>`. Якщо в ідеї є активний план, lead оновлює
  в ньому «що знаємо», впевненість напряму і доливає в чергу питання з прогалин та
  підказок скаутів. Коміт `review(B-###)`.
- **«Копати глибше»** → нові підпитання в brief, підтвердження одним словом, фоновий
  прогін лише для них; `reviewed` знову `null`.
- **Гейт 3** → кроки `/decide` з вибором і причиною редактора.
- **Push** виконується в кінці `/review`, `/decide` і затвердження плану, через запит
  дозволу, як і раніше. Між гейтами коміти накопичуються локально.
- `/review` дозволено викликати моделі (`disable-model-invocation: false`), щоб
  спрацьовувало «показуй B-004» звичайними словами. Гейт цим не обходиться: skill
  лише показує й питає. Решта skills лишаються ручними.

## 6. Частина C — план дослідження

### 6.1 Сутність
`wiki/plans/P-I-###.md`, шаблон `templates/plan.md`, один план на ідею.

```yaml
id: P-I-002
idea: I-002
status: draft         # draft | active | paused | closed
phase: map            # map | depth | synthesis
checkpoint: null      # null | running | ready
started: null
target_decision: null # дату ставить редактор
updated: 0000-00-00
confidence:           # low | medium | high | null, по напрямах
  demand: null
  competition: null
  complexity: null
  economics: null
  entry: null
briefs: []
```

Тіло: `## Ціль` · `## Гіпотеза зараз` · `## Напрями` (п'ять підрозділів) ·
`## Kill-критерії` · `## Фази` · `## Лог`.

`draft` — план чекає затвердження; `paused` — редактор призупинив трек (нові brief'и
не пропонуються); `closed` — по ідеї записано рішення через `/decide`.

### 6.2 П'ять фіксованих напрямів
Однакові для всіх ідей, щоб плани можна було порівнювати.

| Ключ | Напрям | На що відповідає | Рубрика | План MVP |
|---|---|---|---|---|
| `demand` | Попит і ринок | хто платить, скільки їх, розмір bottom-up | market | перший клієнт |
| `competition` | Конкуренти й альтернативи | прямі, непрямі, держава, «нічого не робити» | competition, why_us | позиціонування |
| `complexity` | Складність реалізації | техніка, залізо, команда, строки | fit, time_to_revenue | обсяг MVP |
| `economics` | Економіка | ціна, собівартість, маржа | — | ціна |
| `entry` | Вхід і регуляторика | шлях до першого контракту, юридика, сертифікація | risk, time_to_revenue | шлях входу |

У кожному напрямі чотири блоки:
- **Що знаємо** — 2–4 рядки з посиланнями на теми й докази.
- **Впевненість** — low / medium / high і одне речення чому.
- **Черга питань** — впорядкований список; біля кожного походження: редактор,
  red team, digest B-###.
- **Потрібно від редактора** — розмови, юрист, ручні джерела; посилання на
  `wiki/open-questions.md`.

### 6.3 Фази
| Фаза | Орієнтир | Що відбувається | Умова виходу |
|---|---|---|---|
| `map` Карта | тижні 1–3 | по одному широкому brief'у на напрям | кожен напрям має переглянутий brief або явне «пропустити» від редактора |
| `depth` Глибина | тижні 4–8 | brief'и по найслабших напрямах і kill-критеріях; польові знахідки редактора через `/ingest` | kill-критерії зняті або спрацювали; або редактор каже «досить» |
| `synthesis` Синтез | тижні 9–12 | фінальний аналіз, повний red team, звіт із планом MVP | гейт 3, `/decide` |

Строки орієнтовні; `target_decision` ставить редактор.

### 6.4 Контрольна точка фази
Наприкінці `map` і `depth`: analyst у фоні → red team (full) у фоні → lint → коміт →
`checkpoint: ready` → рядок «контрольна точка готова: `/review I-###`».

`/review I-###` показує ≤ 10 рядків (розмір ринку з діапазоном, головні конкуренти,
три причини провалу від red team, підсумок spot-check, стан kill-критеріїв) і питає:
наступна фаза / змінити гіпотезу / ще раунд доказів / park / kill.
- «Наступна фаза» і «змінити гіпотезу» записуються в `## Лог` плану.
- park і kill ідуть через кроки `/decide`; план отримує `status: closed`.

Сторінки `wiki/analysis/<idea>-analysis.md` і `wiki/redteam/<idea>-redteam.md`
оновлюються на місці (`updated:`); попередні версії лишаються в історії git. Hook
`redteam-gate.mjs` працює без змін.

### 6.5 Skill `/plan I-###` (замінює `/deep-dive`)
- **Плану немає.** Lead читає картку ідеї, digest'и її brief'ів, теми, kill-критерії
  red team, відкриті питання; заповнює «що знаємо» з посиланнями; впевненість ставить
  лише там, де є докази; пропонує до трьох питань у чергу кожного напряму; питає дату
  цільового рішення. Гейт: затвердити / змінити черги / змінити дату / стоп. Після
  «так»: `status: active`, `started`, коміт `plan(I-###): created`, push.
  Якщо ідея ще в `inbox` або `screening`, перехід на довгий трек записується кроками
  `/decide advance` з причиною редактора (`stage: deep-dive`), як і будь-який інший
  перехід між стадіями.
- **План є.** Стан у ≤ 15 рядків: фаза, тиждень, впевненість і довжина черги по
  напрямах, що біжить, що чекає. Пропонує 1–3 наступні brief'и: спершу kill-критерії,
  далі напрями з найнижчою впевненістю. Для вибраних пише brief'и за кроками
  `/research`; гейт 1 можна пройти пачкою; затверджені йдуть у фон за розділом 4.
- **Умова виходу фази виконана** → пропонує контрольну точку (6.4).
- **Синтез:** analyst → red team full → writer → `/review I-###` → гейт 3. Після
  будь-якого фінального рішення план отримує `status: closed`.

Редактор будь-коли змінює план звичайними словами («додай питання…», «підніми…
нагору», «змінюємо гіпотезу»). Lead редагує план, пише рядок у `## Лог`, комітить
`plan(I-###): …`.

### 6.6 План MVP
Новий розділ `## План MVP` у `templates/report.md`, обов'язковий для фінального звіту
ідеї з планом: перший клієнт · обсяг MVP · ціна й економіка · шлях входу · що лишається
неперевіреним.

- Обсяг MVP визначає редактор (гіпотеза в плані). Система підкладає під кожен пункт
  докази.
- Analyst отримує новий розділ `## Основа для плану MVP` у `templates/analysis.md`:
  кандидати в перші клієнти, діапазон цін, драйвери собівартості, кроки входу з
  тривалістю, усе з доказами.
- Writer переносить це в звіт за звичайними правилами: кожне речення з доказом,
  відсутнє — «доказів не знайдено».

### 6.7 Стадії ідеї
Значення `stage` не змінюються. `deep-dive` означає «на довгому треку, план
активний»; `validation` — «рішення advance прийнято, MVP у роботі». Це зафіксовано в
`docs/vision.md`.

## 7. Видимість: `/status`

`scripts/status.mjs` отримує три блоки зверху і прапорець `--waiting` (лише перший
блок, для пропозицій після запуску).

- **Чекає на вас**
  - гейт 1: brief'и `draft`, плани `draft`;
  - гейт 2: brief'и `collected` з `reviewed: null` і `run_stage: null`;
  - гейт 3: звіти по ідеях, де `decided` порожнє або раніше за дату звіту; плани з
    `checkpoint: ready`;
  - відкриті питання до редактора (перші 5).
- **Біжить** — brief'и з `run_stage` (крім `queued`): крок, скільки триває, скільки
  підпитань мають докази й верифікацію; плани з `checkpoint: running`; окремо черга.
  Прогін, що триває понад 3 години, позначається «можливо, обірвано: `/run B-###`».
- **Плани** — ідея, фаза, тиждень N з M, впевненість по напрямах, довжина черги.

| Правила | `CLAUDE.md`: правило 1 (відкладені гейти), правило 8 (push на гейті), схема з рядком Plan, розділ Delegation (фон, verifier одразу за скаутом, ліміт двох, хвости по одному, продовження за `run_stage`), формат чекпоінта |

**Нові перевірки lint**
- План: `id` формату `P-I-###`, ідея існує, `status`, `phase`, `checkpoint` і значення
  `confidence` з дозволених наборів; не більше одного активного плану на ідею.
- Brief: `run_stage` і `workstream` з дозволених наборів; `status: running` вимагає
  `run_stage`.
- Попередження: brief чекає гейту 2 понад 7 днів; активний план не оновлювався 14+
  днів; brief ідеї з активним планом, створений після `started`, без `workstream`.

## 10. Збої
| Ситуація | Поведінка |
|---|---|
| Скаут упав, повернув порожньо або вичерпав ходи | Ланцюжок іде далі з рештою; у digest рядок «скаут №N не завершив»; `/review` пропонує перезапустити №N |
| Джерело недоступне для verifier | Як зараз: `verification: unreachable` |
| Lint червоний після другого проходу librarian | `run_stage` лишається `librarian`, один рядок редакторові з виводом lint |
| Сесія обірвалась | Brief лишається `running`; `/status` показує крок; `/run B-###` продовжує (4.7) |
| Фоновий агент просить дозвіл, якого немає в allow-списку | Виявляється пробою (розділ 11). Рішення про розширення allow-списку приймає редактор; `git push` у список не додається |
| Редактор змінює план під час прогону | Конфлікту немає: прогін пише лише у свій brief, докази, джерела й теми; план оновлюється тільки в `/review` |

## 11. Перевірка

1. **Проба фону (до будь-яких правок).** Один фоновий агент типу `scout`: один пошук,
   один fetch, без запису у wiki. Перевіряється: немає запитів дозволу; сповіщення
   приходить, коли редактор нічого не робить; сповіщення не губиться, коли редактор
   саме пише. Якщо проба не проходить, дизайн переглядається до реалізації.
2. **Скрипти.** `node scripts/lint.mjs` на поточній wiki дає 0 помилок після міграції.
   На тимчасовій копії з навмисно зіпсованим планом і brief'ом lint дає очікувані
   помилки. `node scripts/status.mjs` показує три нові блоки.
3. **Приймальний прогін на I-002.**
   - `/plan I-002` будує план із наявних доказів B-003 без нових пошуків; редактор
     затверджує.
   - Редактор затверджує перший brief; він іде у фон.
   - Під час прогону редактор проходить `/review B-003`.
   - Критерії: сесія жодного разу не заблокована; `/status` посеред прогону показує
     крок; після завершення є рядок «готовий до перегляду» без питання; `## Журнал
     прогону` містить час кожного кроку; lint 0 помилок.

## 12. Порядок робіт
1. Проба фону.
2. Фон: поля brief'у, міграція, `/run`, `/review`, `status.mjs`, lint, правила в
   `CLAUDE.md`. Після цього кроку чекання вже немає.
3. Решта skills у фоні: `/screen`, `/red-team`, `/report`, `/ingest`, `/decide`,
   `/lint`.
4. План: шаблон, `/plan`, розділи плану MVP, lint, librarian, документація;
   видалення `/deep-dive`.
5. Приймальний прогін на I-002.

Кожен крок — окремий коміт; push на перегляді редактора.

## 13. Відкрите для редактора
- **Економіка в рубриці.** Напрям `economics` досліджується, але в бал не потрапляє.
  Додавання критерію — окрема зміна рубрики з датованим записом у «Зміни».
- **`docs/context.md`.** Там очікуваний результат досі «ряд ідей, доведених до
  рішення». Це файл редактора; після сьогоднішніх рішень його варто оновити
  (результат = рішення + план MVP по продукту; ідеї веде редактор).
- **`/review` доступний моделі.** Усі інші skills ручні за вашим рішенням із ретро
  2026-09-09. Тут виняток, щоб «показуй B-004» працювало словами (розділ 5). Якщо
  хочете лишити суто ручним, прибираю.
- **Повернутись через 2–3 тижні роботи:** чи заважає оркестрація в головній розмові;
  якщо так — виносити ланцюжок в окремий виконавець (перший крок до нічних прогонів
  із `docs/vision.md`, v1).
